# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Backend for **BiletFlow**, an event-ticketing platform (university SWE project, SRS v0.3).
Spring Boot 4.1 / Java 21 / PostgreSQL 16, REST API secured with stateless JWT.
Implemented so far: auth, users, organizer profiles, venues, events (with poster images), ticket types, orders, tickets (payments through a built-in simulator or Halyk ePay's test environment), QR images, check-in staff + scanning, append-only audit log.
Also: admin event suspension + role management, organizer sales dashboard API, simulated paid-sales activation, PDF tickets, email + in-app notifications, email verification + password reset, promo codes + Campaign QR, support cases, full-order refunds, organizer event history (events by phase + per-event activity timeline), attendance analytics, platform administration (user search + suspension, search of events/orders/payments/refunds, monitoring overview, reported events, platform fee settings, CSV reports), calendar export (.ics files and Google/Outlook links), simulated organizer payouts, assigned seating (predefined seat maps with standing sections).
Every SRS feature is implemented; not planned: a seat-map editor, several ticket types for one seat, best-available seat picking.
`BiletFlow_SRS_Initial_Draft.pdf` (v0.3, in the user's Downloads) is the requirements source.

## Git workflow (follow these)

- After finishing a feature or fix: commit on a feature branch, push the branch, and open a PR with `gh pr create`. Don't ask first.
- **Never merge PRs and never push directly to `master`.** A merge to `master` deploys to the live server, so the user merges themselves.
- `master` is the default branch. Commit messages loosely follow Conventional Commits, without a Co-Authored-By trailer.

## CI/CD and deployment

`.github/workflows/ci-cd.yml`:
- **`test`** runs on every PR and every push to `master`: `./mvnw -B verify` with `TZ=Asia/Almaty`. Testcontainers uses the runner's Docker.
- **`image`** runs on pushes to `master` only, on an ARM runner. It copies the tested jar into `deploy/Dockerfile` (runtime only, no Maven) and pushes `ghcr.io/nurial911/backend-biletflow:<sha>` and `:latest` for `linux/arm64`. The VM is an Oracle Ampere A1 (aarch64).
- **`deploy`** connects over SSH (secrets `VM_HOST`, `VM_USER`, `VM_SSH_KEY`, `VM_KNOWN_HOSTS`), copies `deploy/deploy.sh` to `~/app` and runs it with the SHA. The script:
  1. runs `pg_dump` into `~/app/backups` (keeps 10);
  2. saves the old `TAG` in `~/app/.env`, writes the new one, then `docker compose pull && up -d`;
  3. polls `http://localhost:8080/actuator/health` for 90 s;
  4. if that fails, restores the old `TAG`, restarts and fails the job;
  5. if it succeeds, runs `docker image prune -f` and removes old SHA images, keeping the previous one.

On the VM, `~/app` holds:
- `docker-compose.yml` (from `deploy/`). It sets project `name: biletflow`, so it keeps the old stack's volumes. Never `down -v`.
- `Caddyfile`.
- `.env` (`TAG`, `DOMAIN`; no secrets).
- `app.env`: all app secrets, loaded with `env_file`, never in git (`deploy/app.env.example` lists the names).

The root `Dockerfile` and `docker-compose.yml` are for local development only. A rollback restores the app, not the database: keep migrations additive (old app versions ignore new columns; Flyway ignores "future" migrations).

```bash

docker compose up --build

# Only Postgres in Docker (published on localhost:5432), backend run locally / from the IDE

# Build / run locally with the Maven wrapper (use mvnw.cmd on Windows)

./mvnw -DskipTests package      # build without tests
./mvnw spring-boot:run          # run locally; needs DB_URL, DB_USERNAME, DB_PASSWORD, JWT_SECRET env vars
./mvnw test                     # run tests (Docker must be running)
./mvnw test -Dtest=ClassName#method   # single test
```

- API: http://localhost:8080 — Swagger UI: http://localhost:8080/swagger-ui.html (use **Authorize** with the `accessToken` from `/api/auth/login`).
- `postman/BiletFlow.postman_collection.json` walks the whole API in order. It needs the seeded admin and scanner (`SEED_DATA=true`), registers its own organizer and attendee on each run, and its email folder needs Mailpit. `postman/halyk-test-checkout.html` opens Halyk's payment page from a `payment-session` response, and is the smallest working example of the frontend's job.
- Tests extend `ApiIntegrationTest` (helpers, over `IntegrationTestBase`): the full app on a random port against a throwaway Testcontainers Postgres, no env vars needed. `CoreFlowIntegrationTest` drives order → payment → ticket → QR → scan over HTTP, including the concurrency cases. Each test creates its own users and event. Use real Postgres, not H2: inventory, payment, promo limits and scan rely on row locks. `ticketType(...)` switches paid sales on with SQL; use `ticketTypeWithoutActivation` to test the gate. Email goes to `CapturingMailGateway`; call `deliverQueuedEmails()` (the background dispatcher is off in tests). `SmtpDeliveryIntegrationTest` uses a real Mailpit container. `HalykPaymentIntegrationTest` uses `FakeHalykServer`, whose responses were captured from Halyk's real test environment.
- ZXing's `PURE_BARCODE` mode is unreliable on non-integer pixel grids: render PDFs at 300 dpi or more when decoding them in tests.
- When running outside Docker, add `-Duser.timezone=Asia/Almaty` (Docker sets it) so `@Future` checks and `LocalDateTime.now()` match user input.

## Configuration

All config comes from env vars (see `.env`, `docker-compose.yml`, `src/main/resources/application.yaml`):
`POSTGRES_DB/USER/PASSWORD` (compose), `DB_URL/DB_USERNAME/DB_PASSWORD`, `JWT_SECRET` (≥64 chars, HS512),
`JWT_EXPIRATION_MS` (default 1 day), `CORS_ALLOWED_ORIGINS`, `DDL_AUTO` (default `validate`; leave it), `SEED_DATA`,
`UPLOADS_DIR` (poster files; default `./uploads`, `/app/uploads` on the `uploads` Docker volume in compose),
`BACKEND_BIND` (compose only; address port 8080 is published on, default `127.0.0.1`, use `0.0.0.0` to reach it from a phone on the LAN),
`APP_FRONTEND_URL` (base of links in emails and Campaign QR codes; must be the https address on a server), `ACTIVATION_FEE_KZT` (default 5000, a placeholder; admins can override it and the processing fee at runtime via `/api/admin/settings`), `PAYOUT_DELAY_HOURS` (default 72, a placeholder: hours after an event ends before its simulated payout),
`MAIL_ENABLED` (default `false`: nothing is sent, only the subject is logged), `MAIL_HOST/PORT/USERNAME/PASSWORD/FROM`, `MAIL_SMTP_AUTH`, `MAIL_STARTTLS`.
For a local email demo set `COMPOSE_PROFILES=mail` and `MAIL_ENABLED=true`, then read messages in Mailpit at http://localhost:8025.
`PAYMENT_PROVIDER` (`simulated` by default, or `halyk`), `HALYK_CLIENT_ID/CLIENT_SECRET/TERMINAL_ID` (required for `halyk`; Halyk publishes a shared test merchant at https://epayment.kz/en-US/docs/Test-credentials), `HALYK_CALLBACK_BASE_URL` (public https address of this backend), `HALYK_TEST_MODE` (default `true`), `HALYK_OAUTH_URL/API_URL/SCRIPT_URL` (default to Halyk's test hosts; production values are `https://epay-oauth.homebank.kz/oauth2/token`, `https://epay-api.homebank.kz`, `https://epay.homebank.kz/payform/payment-api.js`).

- `.env` holds real secrets — never commit it, never print its values.
- **Schema is owned by Flyway** (`src/main/resources/db/migration`); Hibernate only validates (`ddl-auto=validate`), so the app refuses to start if an entity and the schema disagree. Every entity change needs a new `V<n>__<what>.sql`; never edit a migration that has already run anywhere. `V1__baseline.sql` is the schema Hibernate generated on 2026-11-19; databases created before that by `ddl-auto=update` have no Flyway history and are marked as V1 on first start (`baseline-on-migrate`), so V1 runs only on empty databases.
- `@Enumerated(STRING)` columns have a CHECK constraint `<table>_<column>_check` listing the allowed values (V1 got them from Hibernate). A new enum value needs a migration that drops and re-adds it (see `V2__refunds.sql`), or inserts fail. `AuditLog.action` and `Notification.type` are plain strings on purpose and need no migration.

**YAML nesting matters:** `jwt` lives under `spring:` (read by `JwtConfig` as `spring.jwt.*`), while `app`, `server` and
`springdoc`, `management` must stay at the top level (`app.seed.enabled`, `app.cors.allowed-origins` are read by `DataSeeder` / `SecurityConfig`).
Indenting them under `spring:` silently disables `SEED_DATA` and `CORS_ALLOWED_ORIGINS`.

## Architecture

Package root: `kz.edu.biletflow.backend`. Classic layered design:

```
controllers/        interfaces holding ALL Spring annotations (@RequestMapping, @PreAuthorize, @Valid, ...)
controllers/impl/   @RestController classes implementing them — no annotations on parameters, just delegate
services/           service interfaces;  services/impl/  @Service implementations with business rules
repositories/       Spring Data JPA (custom JPQL for visibility queries)
entities/           JPA entities + enums (Lombok @Getter/@Setter, not @Data)
dtos/               request/response DTOs (Lombok @Data, jakarta.validation annotations)
mappers/            MapStruct mappers (componentModel = "spring")
security/           JWT filter/service, UserPrincipal, auth controller + service (login/register)
configs/            SecurityConfig, JwtConfig, OpenApiConfig, DataSeeder
exception/          custom exceptions + GlobalExceptionHandler (@RestControllerAdvice)
```

### Conventions to follow when adding features

- **New endpoint** → add the method with annotations to the controller *interface*, implement in `impl/`, put logic in the service impl. Controllers never touch repositories.
- **Current user** → `@AuthenticationPrincipal UserPrincipal currentUser` (has `getId()`, `getEmail()`, `hasRole("X")`). It is `null` on anonymous requests to public GET endpoints — null-check it.
- **Roles**: `ATTENDEE`, `ORGANIZER`, `EVENT_ADMIN`, `PLATFORM_ADMIN` (`User.Role`). The JWT carries `role` and `id` claims; authorities are `ROLE_<role>`. Use `@PreAuthorize("hasRole('ORGANIZER')")` on the interface.
  Role is read from the token, not the DB — a role change requires issuing a new token (see `OrganizerProfileServiceImpl.createProfile`, which returns one).
  The only DB read per request is `JwtAuthenticationFilter` checking the account still exists and isn't suspended (`UserRepository.findSuspendedById`): a suspended account gets 403, a deleted one is treated as anonymous.
- **Public routes** are set in `SecurityConfig`: `/api/auth/**`, Swagger, and **all GET** under `/api/events/**` and `/api/venues/**`. Anything new under those GET paths is public automatically — enforce visibility in the service.
- **Errors**: throw the custom exceptions, never return error bodies by hand:
  `ResourceNotFoundException` → 404, `ForbiddenOperationException` → 403, `DuplicateResourceException` → 409,
  `BusinessRuleViolationException` → 400 (domain rules), `BadCredentialsException` → 401. Response shape is `ErrorResponse {status, message, timestamp}`. Unknown exceptions → generic 500 without leaking messages.
- **Ownership checks** live in services (`getOwnedEvent`, `getOwnedTicketType`) and throw 403.
- **Hidden-existence rule**: if a requester may not see an event (not PUBLISHED, or PRIVATE, and not owner/admin), respond **404, not 403**, so its existence isn't revealed.
- **Mapping**: use MapStruct. Partial updates (PUT with optional fields) use `@BeanMapping(nullValuePropertyMappingStrategy = IGNORE)` — null means "leave unchanged". Explicitly `ignore` id, relations, status/hidden and timestamps; relations are resolved in the service.
- **Status changes** never go through plain update DTOs — they have dedicated endpoints (`/publish`, `/unpublish`, `/cancel`, `/hide`, `/unhide`).
- Create endpoints return **201** with a `Location` header (`ServletUriComponentsBuilder`). Lists are paged (`Pageable` → `Page<Dto>`), except ticket types (plain `List`).
- Mark write methods `@Transactional`, reads `@Transactional(readOnly = true)`. `open-in-view` is off, so touch lazy relations inside the transaction.
- **Audit**: organizer, staff, admin and payment actions call `AuditService.record(...)` inside the action's own transaction (it is `MANDATORY`), so they commit or roll back together. Add new actions to `AuditAction`. `AuditLogRepository` only exposes `save` and the timeline query; entries are never edited or deleted. Organizers read descriptions in the event timeline: don't put ticket codes, secrets or other buyers' details in them. Give the entry the event's id whenever the action belongs to an event, or it won't appear in the timeline.
- **Notifications**: tell a user about something with `NotificationService.notifyUser(s)` inside the action's transaction (`MANDATORY`); add new kinds to `NotificationType`. The row is both the in-app notification and the queue entry for its email: `NotificationEmailDispatcher` sends it within seconds and retries for about 30 minutes, so a mail outage can't fail or lose anything. Never put sign-in or reset links in a notification: `AccountEmailServiceImpl` mails those directly and stores only their hash.
- Times are `LocalDateTime` (Asia/Almaty, no zone stored). Money is `BigDecimal(12,2)` in KZT; price 0 = free.

## Domain rules (implemented)

- **Users**: register always creates `ATTENDEE`. Soft delete (`@SQLDelete` sets `is_deleted`, `@SQLRestriction` hides deleted rows). Admin endpoints under `/api/users`, self-service under `/api/users/me`.
  Registering emails a confirmation link; `User.verificationStatus` records it, and changing the address clears it. Nothing is blocked for an unverified address yet. `/api/auth/verify-email`, `/resend-verification`, `/forgot-password`, `/reset-password`: links are single-use (24 h / 1 h), and `resend` and `forgot` answer 204 for unknown addresses and send at most one email a minute. A password reset doesn't revoke JWTs already issued.
  `PUT /api/users/{id}/role {role}` (admin) is the only way to grant `EVENT_ADMIN`/`PLATFORM_ADMIN`. Rules: not on yourself; `ORGANIZER` only if the user has an organizer profile; an organizer who owns events can't be moved off ORGANIZER; leaving `EVENT_ADMIN` deletes the user's staff assignments. The user must log in again for the new role to take effect (old token keeps the old role until it expires).
- **Organizer profile**: an ATTENDEE calls `POST /api/organizers/profile` → becomes ORGANIZER, gets a new token. One profile per user.
  Simulated identity check: `POST /api/organizers/profile/verification` → PENDING, a PLATFORM_ADMIN decides via `GET /api/organizers/verification-requests` and `POST /api/organizers/{profileId}/verification {approved, note}`; REJECTED can ask again. `PUT /api/organizers/profile/payout-account {bankName, accountHolder, iban}` is simulated too and keeps only the last 4 IBAN characters.
- **Paid-sales activation** (`/api/events/{id}/activation`, per event, all simulated): paid tickets can't be ordered or paid until `Event.paidSalesActive` is true; free tickets ignore it. Checklist (`GET`, owner/admin): paid ticket type, verified organizer, payout account, `POST /pay-fee` (`app.payments.activation-fee-kzt`, reference `SIM-…`), `POST /accept-terms`; then `POST /activate` (400 naming what's missing). `POST /suspend {reason}` / `/unsuspend` are PLATFORM_ADMIN: new paid orders and payments stop, free tickets and sold tickets keep working, unpaid orders simply run out. `GET /api/admin/paid-sales-activations?status=`. Not copied by `duplicate`. Only `PaidSalesActivationServiceImpl` changes the flag.
- **Venues**: created by ORGANIZER or PLATFORM_ADMIN; listing is public. `capacity` is required on create (column stays nullable for legacy rows; null = no limit), unless `seatingLayout` is given: then the capacity is the layout's (another value is 400). Only a PLATFORM_ADMIN changes a venue's layout afterwards (`PUT /api/venues/{id}/seating-layout`, audit `VENUE_SEATING_LAYOUT_CHANGED` without event id).
  Event capacity must be ≤ venue capacity (checked on event create/update); an event created without capacity inherits the venue's.
- **Events**: status `DRAFT → PUBLISHED ⇄ DRAFT`, any → `CANCELLED` (terminal; cancelled events can't be edited/published). Visibility `PUBLIC` (listed), `UNLISTED` (open by link, not in lists), `PRIVATE` (owner/admin only).
  Timing: registration opening < closing ≤ start < end (all optional except start). `duplicate` copies as a new DRAFT (ticket types not copied).
  Public list = PUBLISHED + PUBLIC, plus the requester's own events; PLATFORM_ADMIN sees everything.
- **Event posters**: `POST /api/events/{id}/poster` (multipart, part `file`; organizer only, not on CANCELLED) replaces the poster, `DELETE` removes it, `GET` serves it (same visibility as the event → 404).
  JPEG/PNG/WebP up to 5 MB (413 above), type detected from magic bytes (`PosterFormat`), no resizing. Files live in `UPLOADS_DIR` as `<uuid>.<ext>` (`PosterStorage`); `Event.posterKey` holds the name.
  `EventResponse.posterUrl` is absolute with `?v=<key>`, so the GET is cached for 30 days. File deletes run after commit; new files are removed on rollback. `duplicate` copies the poster file.
- **Ticket types**: belong to an event; only its organizer can create/update/hide. Sum of quantities (hidden included) must not exceed event capacity. Sales window must end before event start. Hidden types are visible only to owner/admin. `sold` = PAID + unexpired PENDING order items; price can't change and quantity can't drop below `sold` once any are sold/reserved. In an assigned-seating event the quantity comes from the seat map: create without it (stored 0), and a PUT that changes it is 400.
- **Assigned seating** (SRS 4.3.1; `SeatingServiceImpl`, `SeatingLayouts`, tables `event_sections`/`event_seats` V6): `Event.seatingMode` is `GENERAL_ADMISSION` (default, unchanged behaviour; also the answer for a venue without seats, such as a field) or `ASSIGNED`. Layouts are predefined JSON files in `resources/seating/` (`concert-hall`: 488 seats; `arena`: 10 000 seats in four stands + a 6 000-place standing field), validated at startup; no editor. Sections are `SEATED` (rows of numbered seats) or `STANDING` (a capacity, sold by count). `GET /api/venues/seating-layouts` is public.
  Organizer (`/api/events/{id}/seating`): `PUT {mode}` copies the venue's layout into the event's own sections and seats (one JDBC batch insert), sets the event capacity to the layout's and every ticket type's quantity to 0; back to general admission deletes them. Both only while the event has **no orders at all** (it takes the ticket type locks first, so an order in flight is seen). `PUT /sections/{sectionId} {ticketTypeId|null}` links a section to its price category: a standing section needs a ticket type of its own, a seated type can span sections; refused while the section has sold or held tickets. `PUT /seats {seatIds, blocked}` takes seats off sale (not sold or held ones). Every change recomputes the linked ticket types' quantities (unblocked seats + standing capacity). `GET` is the setup view (organizer/admin, others 404). While ASSIGNED, the event's venue and capacity can't change. `duplicate` copies the seat map and blocked seats, not the section links. Audit `SEATING_*`, `SEATS_BLOCKED/UNBLOCKED`.
  Public map: `GET /api/events/{id}/seat-map` (sections with price, available/held/sold/blocked, map geometry; 400 for general admission) and `/seat-map/sections/{sectionId}` (seats with x/y, accessible, status `AVAILABLE`/`HELD`/`YOURS`/`SOLD`/`UNAVAILABLE`); visible like the ticket types, a hidden ticket type's price stays hidden. Clients poll; there is no push.
  Buying: `POST /api/orders` (and `/quote`) take `seatIds` (max 50) next to `items`; standing sections are ordered as `items` with a quantity, seated ticket types only by seat. **The unpaid order is the seat hold**: no seat state is stored, a seat is taken while a PAID or unexpired PENDING order item points at it, so cancel, expiry and refund free it by themselves. Locks: promo campaign → ticket types (id order) → seats (id order), then the seats are re-read from the database; a taken, blocked or relinked seat is 409 (`SeatUnavailableException`) naming the seats. One order item per seat (quantity 1) with section/row/seat copied onto it and onto the ticket; a partial unique index allows one VALID/USED ticket per seat. `seatLabel` ("Stalls, row A, seat 5") is on order items, tickets (so check-in and attendee search), the PDF and the confirmation email.
- **Orders**: `POST /api/orders` (any authenticated user) reserves inventory for `app.orders.hold-minutes` (default 15) under a row lock on each ticket type (`findByIdForUpdate`). Free orders (total 0) are PAID immediately; otherwise, in the default simulated mode, `POST /api/orders/{id}/pay` (no provider, no money moves) → PAID and issues one `Ticket` (UUID `code`, for the QR) per unit. Each attempt writes a `Payment` (`simulated=true`, reference `SIM-<uuid>`, listed by `GET /api/orders/{id}/payments`). Optional body `{"simulatedOutcome":"DECLINED"}` answers 402, keeps a FAILED payment (`noRollbackFor`), issues nothing and leaves the order PENDING for a retry. `app.payments.processing-fee-percent` (default 2.5, a placeholder) is deducted from the organizer's payout, not added to the attendee's total. `attendeeName` on the order is optional, defaults to `User.fullName` then email, and is copied to each ticket. Pay and cancel lock the order row (`findByIdForUpdate`) so concurrent requests can't issue tickets twice. `PENDING → CANCELLED` by owner, `PENDING → EXPIRED` by `OrderExpiryScheduler` (every minute). Others' orders/tickets return 404. Endpoints: `/api/orders`, `/api/tickets`; `GET /api/tickets/{id}/qr` returns a PNG of the ticket `code` (owner/admin).
- **Halyk ePay** (`PAYMENT_PROVIDER=halyk`; `PaymentSessionServiceImpl`, `HalykClient`, table `payment_sessions`): `POST /api/orders/{id}/pay` is refused, because it would let buyers mark their own orders paid. `POST /api/orders/{id}/payment-session` returns `{provider, simulated, scriptUrl, payment}`; the browser loads `scriptUrl` and calls `halyk.pay(payment)`, so card numbers never reach this server (in simulated mode it returns `provider: SIMULATED` and the frontend calls `/pay`). The shopper returns to `APP_FRONTEND_URL/orders/{id}/payment-result?status=success|failure`, and that page calls `POST /api/orders/{id}/payment-check`.
  The bank's status API is the only source of truth. `POST /api/payments/halyk/callback` (public) just prompts a check, and `PaymentSessionScheduler` checks every 15 s, which is what completes payments locally where the bank can't reach the callback. The bank first holds the money (`AUTH`); we re-check the order under its row lock, capture (`CHARGE`), and only then issue tickets. A session stays `OPEN` through declines, since the bank's page allows 3 attempts, and each decline writes a FAILED `Payment`. Money we can't accept (order cancelled or expired, wrong amount, paying twice from two tabs, paid sales suspended) is released: `cancel` if held, `refund` if taken, with a FAILED `Payment` and a notification. Opening a session extends the reservation to the page's 20 minutes, capped at hold + 20 minutes from order creation. The activation fee is still simulated.
  Halyk's docs are partly out of date. Confirmed by real test payments: `testoauth.homebank.kz` (404) and `testepay.homebank.kz` (timeout) are dead; tokens last 20 minutes (`expires_in` is a string), not 2 hours; the page needs an email or phone, so we pre-fill the buyer's email. Not yet confirmed: delivery of the real result call, which needs a public address. `Payment.simulated` stays true while `HALYK_TEST_MODE=true`, as SRS 4.6 requires.
- **Refunds** (`RefundServiceImpl`, table `refunds`, SRS 4.9): `POST /api/orders/{id}/refund {reason?}` (organizer of the event or PLATFORM_ADMIN; other organizers 404, attendees 403) refunds a PAID order in full; `GET /api/orders/{id}/refunds` (buyer, organizer, admin). Whole orders only (the SRS asks for full refunds). Refused (400) unless the order is PAID, while a refund is PENDING, or if any of its tickets is checked in (undo the check-in first). Orders of a cancelled event can be refunded.
  The order's tickets → REFUNDED at once (scan answers `REFUNDED` "This ticket was refunded", PDF 400), order → REFUNDED, its tickets go back on sale, `REFUND_COMPLETED` notification without ticket attachment, audit `ORDER_REFUNDED`. A simulated payment is refunded in one transaction (`SIM-REFUND-…`). A Halyk payment: PENDING refund under the order lock, `HalykClient.refund` outside any transaction, then SUCCEEDED, or FAILED with the tickets valid again (502, audit `REFUND_FAILED`, the organizer can retry). `PaymentSessionScheduler` also calls `reconcilePendingRefunds()`: a refund PENDING for over 2 minutes is completed if the bank says `REFUND`, otherwise marked FAILED. A free order is not refunded but its registration is cancelled: order and tickets → CANCELLED, no refund record, `REGISTRATION_CANCELLED`.
  `Event.refundPolicy` (≤2000 chars) is the organizer's own text, shown on the event and copied by `duplicate`; it isn't enforced.
- **PDF tickets**: `GET /api/tickets/{id}/pdf` (owner/admin; 400 for a CANCELLED or REFUNDED ticket). A4, one ticket per page, black on white, vector QR at a fixed position (`TicketPdfGenerator`), embedded Liberation Sans for Kazakh and Russian. The QR holds the same `code` as the digital ticket, so there is only ever one admission. Confirmation emails attach all of an order's tickets as one PDF (plus the event's .ics file).
- **Calendar export** (`CalendarService`, `EventCalendar`, SRS 4.11): `GET /api/events/{id}/calendar.ics` (RFC 5545, `text/calendar`, `no-cache`) and `GET /api/events/{id}/calendar` (`icsUrl`, `googleCalendarUrl`, `outlookUrl`, `office365Url`; only `icsUrl` for a cancelled event). Visible like the event, **plus anyone holding a ticket for it** in any status, so a cancelled or suspended event's file still reaches its attendees; everyone else 404. Nothing asks for access to anyone's calendar.
  UID `event-<id>@<APP_FRONTEND_URL host>` never changes; `SEQUENCE` is `Event.calendarSequence` (V4), raised by every event update and by cancel, so a newer file replaces the entry added earlier. Cancelled = `STATUS:CANCELLED`, "Cancelled: " title, still `METHOD:PUBLISH`. Times use `TZID=Asia/Almaty` with a VTIMEZONE built from the JVM's zone rules; no end time = end of the start day (`EventPhase.effectiveEnd`). Lines are escaped and folded at 75 octets.
  Emails: `ORDER_CONFIRMED` attaches the .ics next to the ticket PDF, `EVENT_UPDATED` and `EVENT_CANCELLED` attach it via `Notification.eventId` (V4; use the `notifyUsers(..., eventId)` overload). Attachments are built when the email is sent, from the event's current state. `OutgoingMail` holds a list of attachments with their content types.
- **Promo codes** (`PromoCampaignServiceImpl`, SRS 4.14): one server-generated code and one opaque token per campaign. `/api/events/{id}/campaigns` (POST, GET, `/{cid}`, `/{cid}/disable`, `/{cid}/enable`, `/{cid}/qr`); reads are owner/admin, anyone else 404. `GET /api/events/{id}/promo?code=` or `?token=` is public and validates for the event page. `POST /api/orders/quote` takes the order body and reserves nothing.
  `promoCode` on the order: discount is calculated only by the server, percent or fixed KZT (fixed = per order), applied to the campaign's ticket types (none listed = all) and capped at their subtotal. A rejected code fails the order with a clear 400. The redemption limit counts PAID + unexpired PENDING orders under a row lock on the campaign, taken before the ticket-type locks. The QR is `APP_FRONTEND_URL/events/{id}?promo=<token>`, indigo with a frame so it can't pass for an admission QR, and `scan` answers INVALID for it. `Order.totalAmount` is after discount; processing fees use it.
- **Support cases** (`/api/support/cases`, SRS 4.13): `POST` (`type` ATTENDEE by default or PLATFORM, `category`, `subject`, `message`, and `ticketId`/`orderId`/`eventId`), `GET ?status=&escalated=&eventId=` (eventId only narrows what the user may already see), `GET /{id}` (case + thread; clients poll), `POST /{id}/messages`, `/assign {email}`, `/status {status}`, `/escalate`.
  ATTENDEE cases: requester, the event's organizer and its assigned staff, and platform admins. PLATFORM cases: the organizer and platform admins. Everyone else gets 404; a requester trying a staff action gets 403. Context is resolved by the server from what the requester owns. A requester's reply reopens a RESOLVED case; staff must change the status first. Staff appear as a team name, and assignee details are hidden from the requester.
- **User administration** (PLATFORM_ADMIN, SRS 4.12): `GET /api/users?q=&role=&suspended=` searches (`q` = part of email or name, case-insensitive and literal, or the exact id; deleted users never appear). `POST /api/users/{id}/suspend {reason?}` (≤500 chars) / `/unsuspend`: not on yourself or another PLATFORM_ADMIN (demote first).
  A suspended user can't log in (403 naming the reason, only after a correct password) and every token already issued gets 403, public GETs included; unsuspend makes those tokens work again. Their PENDING orders → CANCELLED, PAID orders and tickets stay valid (refunds are separate). Nothing else changes: an organizer's events keep selling (suspend the events too if needed) and staff assignments stay. `ACCOUNT_SUSPENDED`/`ACCOUNT_REINSTATED` notifications reach them by email; audit `USER_SUSPENDED`/`USER_UNSUSPENDED`. Columns `users.is_suspended`, `suspended_at`, `suspension_reason` (V3).
- **Admin console** (`/api/admin`, `AdminController`, PLATFORM_ADMIN only, SRS 4.12). Searches share one `q` rule (`SearchText`): case-insensitive substring, `%`/`_` literal, and also the exact id when numeric (so a number can match digits in references and emails too).
  `GET /overview` (counts: suspended users/events, pending verifications, open reports, suspended paid sales, failed payments 24 h / 7 days, pending refunds, failed refunds 7 days, escalated unresolved support cases). `GET /events?q=&status=&suspended=&organizerId=` (title, organizer email, id; drafts/private/suspended included; default sort `startTime` desc), `/orders?q=&status=&eventId=` (buyer email, attendee name, order id), `/payments?q=&status=&provider=&from=&to=` (reference, buyer email, order id; `status=FAILED` = payment failures; dates inclusive), `/refunds?q=&status=`, `/campaigns?eventId=&enabled=` (promo activity, same stats as the organizer's campaign list). Search pages load their relations with `@EntityGraph` overrides of `findAll(spec, pageable)`.
  **Reported events**: `POST /api/events/{id}/reports {reason, message?}` (any signed-in user who can see the event → else 404; not its organizer → 400; one OPEN report per user and event → 409, partial unique index) → 201. `GET /api/admin/event-reports?status=&eventId=&reason=`, `GET /{id}`, `POST /{id}/review {outcome: DISMISSED|ACTIONED, note?}` (only OPEN ones). Reviewing doesn't touch the event (suspend it separately); the reporter gets `EVENT_REPORT_REVIEWED` without the note; audit `EVENT_REPORT_REVIEWED` is recorded **without** an event id on purpose, so organizers never see reports in their timeline. Table `event_reports` (V3).
  **Platform settings**: `GET`/`PUT /api/admin/settings {activationFeeKzt?, processingFeePercent?}` (null = unchanged; fee 0–1 000 000, percent 0–50). Single row `platform_settings` (id 1, inserted by V3); a NULL column falls back to `app.payments.*`. Read all fees through `PlatformSettingsService` (`OrderFulfillment.processingFee`, `PaidSalesActivationServiceImpl`), never `@Value`. Each `Payment` and activation keeps the fee it was charged, so a change only affects later ones. Audit `PLATFORM_SETTINGS_UPDATED`.
  **CSV reports**: `GET /reports/events.csv` (events starting in the range, with the sales API's totals via `SalesService.getEventsSales`) and `/reports/payments.csv` (every attempt, with `simulated`), `?from=&to=` inclusive, default last 30 days, max 366 days. `CsvWriter`: UTF-8 BOM, CRLF, RFC 4180 quoting, and text cells starting with `= + - @` get a leading `'` (CSV injection).
- **Payouts** (simulated, SRS 3.2/4.10; `PayoutServiceImpl`, `PayoutScheduler` every 5 min, table `payouts` V5): one payout per event that ended (`EventPhase.effectiveEnd`) with a PAID order above 0 KZT, created `SCHEDULED` for end + `PAYOUT_DELAY_HOURS`. On its date it is `PAID` with reference `SIM-PAYOUT-…`, `simulated=true` and the destination's bank name + IBAN last 4. The amount is the sales API's `estimatedPayout` (gross − discounts − refunds − processing fees), recalculated at payment, with the breakdown stored on the row.
  Blockers put it `ON_HOLD` with a `holdType`: `NO_PAYOUT_ACCOUNT`, `EVENT_SUSPENDED`, `ORGANIZER_SUSPENDED` (cleared by themselves on a later run) or `ADMIN` (only `/release` clears it). A PENDING bank refund just delays it. A cancelled event, or nothing left after refunds → `CANCELLED` with `statusReason`. Each transition notifies the organizer (`PAYOUT_STATUS`, once per cause) and is audited with the event id (`PAYOUT_*`); scheduler actions have no actor and show as "BiletFlow" in the event history (`AuditService.record` accepts a null actor).
  **No refunds after a PAID payout** (400): `RefundServiceImpl.start` calls `PayoutService.ensureRefundAllowed`, which locks the payout row (payments lock it too), so a refund and the payout of the same event never overlap. Refunds stay possible while the payout is SCHEDULED or ON_HOLD.
  Endpoints: `GET /api/organizer/payouts?status=` (own), `GET /api/organizer/events/{id}/payout` (organizer of the event or admin; others 404; 404 until scheduled). Admin: `GET /api/admin/payouts?q=&status=&organizerId=&eventId=`, `GET /{id}`, `POST /{id}/hold {reason}`, `/release` (pays at once if already due), `/pay-now` (ignores the date, not the blockers), `GET /api/admin/reports/payouts.csv`. Overview has `scheduledPayouts`, `payoutsOnHold`. Tests call `PayoutService.runPayouts()`; the scheduler is off there.
- **Event suspension** (moderation, PLATFORM_ADMIN only): `POST /api/events/{id}/suspend` (optional body `{reason}`, ≤500 chars) / `/unsuspend`. A separate `suspended` flag, not a status, so unsuspend restores the previous state; CANCELLED events can't be suspended.
  A suspended event is invisible to everyone but owner/admin (404, also hidden from lists and its ticket types), new orders and payments are refused, and PENDING orders → CANCELLED. PAID orders/tickets stay valid and check-in keeps working.
  The organizer can still see it (with `suspensionReason`) and cancel it, but every other change (edit, publish/unpublish, duplicate, poster, ticket types) is a 400.
- **Organizer sales** (`/api/organizer`, `SalesService`): `GET /sales/events[?eventIds=1,2]` (ORGANIZER; own events + `totals`), `GET /events/{id}/sales?from=&to=&ticketTypeId=` (adds `salesByDay` by payment date; the three filters narrow only `salesByDay`, never the totals), `GET /events/{id}/orders?status=&q=` (paged, `q` = part of buyer email). Event sales also carry `ticketsRemaining` (capacity − sold − reserved, ≥ 0) and `percentSold` (one decimal), both null without a capacity. Per-event endpoints also allow PLATFORM_ADMIN; anyone else (incl. foreign ids in `eventIds`) gets 404.
  Counting: `ticketsSold` = PAID orders (free tickets count, revenue 0); `ticketsRefunded`/`refundedOrders` = REFUNDED orders, whose tickets are back on sale; `revenue` is gross = PAID + REFUNDED orders at `OrderItem.unitPrice` snapshots (same for `salesByDay`); `discounts` = promo discounts on PAID + REFUNDED orders; `refunds` = SUCCEEDED refunds; `netRevenue` = revenue − discounts − refunds; pending = unexpired PENDING (reserved, not revenue); cancelled/expired counted separately; `processingFees` = SUCCEEDED payments of PAID orders (none on refunded ones), `estimatedPayout` = net revenue minus fees. All figures come from grouped queries (`OrderItemRepository.aggregateSalesByTicketType`, `OrderRepository.countOrdersByEvent`), not per-order loops.
  Note: `TicketTypeResponse.sold` (public endpoint) means PAID + reserved; the sales API splits them into `sold` and `reserved`.
- **Attendance** (`GET /api/organizer/events/{id}/attendance?ticketTypeId=&interval=`, `AttendanceService`, SRS 4.15; organizer of the event or PLATFORM_ADMIN, others 404, check-in staff 403 by role and use `/api/check-in/events/{id}/stats`): ticket holders = VALID + USED tickets (refunded/cancelled don't count), `checkedIn` = USED, `absent` = the rest, `checkInRate` in percent with one decimal (0 with no holders), per ticket type (hidden included), `undoneCheckIns` from `check_in_records`, `firstArrival`/`lastArrival`.
  `arrivals` groups current check-ins by `Ticket.usedAt` (an undo clears it, so arrivals always match `checkedIn`) into `interval` minutes (5, 10, 15, 30, 60, 120, 1440; default 15) with PostgreSQL `date_bin` aligned to midnight; only intervals with arrivals, each with a running `cumulative`. `ticketTypeId` narrows every figure; a type of another event is 404.
- **Organizer event history** (`/api/organizer/events`, `EventHistoryService`, SRS 4.16): `EventResponse.phase` is `UPCOMING`/`ACTIVE`/`COMPLETED`/`CANCELLED`, derived from the clock and never stored (`EventPhase`; independent of DRAFT/PUBLISHED; no end time = lasts until the end of its start day). `GET /api/organizer/events?phase=` (ORGANIZER) lists own events, suspended ones included, newest start first; its query repeats `EventPhase.of`'s rules, so change both together.
  `GET /events/{id}/history?from=&to=&action=&entityType=` (organizer of the event or PLATFORM_ADMIN; others 404, check-in staff 403 by role) reads `audit_log` newest first: `from`/`to` are inclusive dates, `action` is repeatable, `entityType` is the `AuditAction` group; unknown values are 400; client `sort` is ignored. Entries carry the actor's current role; to organizers a platform admin appears as "BiletFlow Support" without id or email, as in support cases.
- **Event cancel** also flips the event's VALID tickets → CANCELLED and PENDING orders → CANCELLED (bulk updates). PAID orders stay PAID until the organizer refunds them one by one (no automatic or bulk refund yet).
- **Check-in staff**: the organizer assigns `EVENT_ADMIN` users by email via `/api/events/{eventId}/staff` (POST/GET/DELETE). The GET is public at the filter level, so the service returns 404 to anyone but owner/admin.
- **Check-in** (`/api/check-in/**`, roles EVENT_ADMIN/ORGANIZER/PLATFORM_ADMIN; allowed for assigned staff, the event's organizer, admins — others get 404): `GET /events` (assigned events), `POST /events/{id}/scan {code}`, `POST /events/{id}/tickets/{ticketId}/undo`, `GET /events/{id}/attendees?q=` (part of email or name, or exact code), `GET /events/{id}/stats`.
  A scan always answers **200** with `CheckInResult` (`CHECKED_IN, ALREADY_USED, CANCELLED, REFUNDED, WRONG_EVENT, INVALID`) — the scan result is data for the app, not an error. Tickets are row-locked during scan/undo; every check-in and undo is appended to `check_in_records`.
